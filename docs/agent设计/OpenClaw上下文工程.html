上下文工程报告：用有限窗口撬动无限任务 ​

结合《上下文工程》与《粘贴的文本》两份材料整理，面向开源技术文档场景。

一、核心矛盾 ​

无限任务复杂度 vs 有限上下文窗口。

AI Agent 处理复杂任务（写长篇报告、全网检索验证、做视频）时，会产生海量中间信息：搜索网页、报错日志、历史记忆、多帧画面、资料条目。如果全部塞给大模型，会导致三个问题：

问题表现
上下文爆炸（Context Overflow）Context Window 有限（如 128k token），塞不下，本轮直接失败或被迫从中间截断，截掉的可能是目标
注意力稀释（Attention Dilution）大量无关原文、旧话题、整页网页夹在提示中间，模型丢掉当前要完成的那一句；中段内容尤其容易被忽略（Lost in the middle）
成本与延迟上升每轮重发一大段历史；定时唤醒若也带上全部历史，花费按唤醒次数乘上去，推理速度极慢

解决思路：按需供给（On-Demand）与过滤（Filtering）。

海量的中间过程留在模型外面，由运行时、专用节点或工具消化，窗口里只留下当前这一步要看的内容。

二、三大上下文工程策略 ​

策略一：宏观架构——Subagent 与上下文折叠 ​

核心理解：主 Agent 不自己做所有搜索和阅读，采用分而治之的层级架构。

  • 主 Agent（Manager/Planner）：负责拆解任务，规划子任务，统筹全局。
  • Subagent（Worker/Searcher）：负责执行具体搜索和阅读。例如派发一个 Subagent 去查某人的出版物，它去 Google Scholar 搜索、阅读十几篇论文摘要，最后只把总结后的一句结论返回给主 Agent。

上下文折叠（Context Folding）：

  • Subagent 探索过程中产生的几十万垃圾文本（整个网页 HTML、不相关论文全文），在任务结束时被“折叠”或“丢弃”。
  • 只有提炼出的关键事实（Fact）被加入主 Agent 的上下文。
  • 节点用过的原文随节点结束丢弃，不追加到主会话。

上下文长度曲线的锯齿状下降：

长度
 ↑
 │    ╱╲          ╱╲          ╱╲
 │   ╱  ╲        ╱  ╲        ╱  ╲
 │  ╱    ╲______╱    ╲______╱    ╲______
 │ ╱                                      ╲
 └──────────────────────────────────────────→ 步骤
   Subagent执行   折叠    Subagent执行   折叠
  • 上升阶段：主 Agent 正在执行复杂搜索，或 Subagent 正在汇报探索结果，上下文增加。
  • 下降/停滞阶段：一个 Subagent 任务完成，其“工作记忆”（大量冗余文本）被清理（Context Pruning/Summarization），主 Agent 只保留最终结论，上下文长度大幅下降，腾出空间给下一个步骤。

并行节点：

  • 几个节点并行时（例如一边组织要说的话、一边决定动作），它们不互相转发中间文本。
  • 每条并行分支只看见开场装入的那份状态，以及自己这一支的材料。
  • 分支之间只在结束时把各自的结论汇合，交给通道一起下发。

执行节点不再往下派生新的节点：

  • 派生一层，就会再产生一份无人折叠的中间文本，锯齿下降就消失了。
  • 需要多步时，由规划阶段一次写明串行顺序，后一步只接收前一步的结论。

一句话总结：Subagent 在底层疯狂搜索，产生大量垃圾文本，但只把提炼后的最终结论返回给主 Agent。主 Agent 的上下文始终保持精简。

策略二：记忆读取——按需检索与精准切片 ​

核心问题：为什么读 Memory 需要特别的工具？

普通 ChatGPT 对话中，记忆通常直接拼接（Inject）到 Prompt 最前面。但在复杂 AI Agent 中，直接把记忆库（MEMORY.md 和 memory/*.md）全部塞进上下文会面临上述三个致命问题。

解决方案：在 System Prompt 中制定规则——

在回答任何关于先前工作、决定、日期、人员、偏好或待办事项之前：先对 MEMORY.md + memory/*.md 执行 memory_search；然后使用 memory_get 仅提取所需行。

过滤流程：

  1. memory_search（搜索定位）：不读取全文，像搜索引擎一样，根据当前问题在记忆文件中找到相关片段/位置，大大缩小范围。
  2. memory_get（精准读取）：读取特定的记忆 Markdown 文件，可以指定起始行（starting line）和读取行数（N lines）。相当于 tail 或 sed 命令，只把真正需要的几行内容拉入当前上下文窗口。

对比：

传统方式OpenClaw 方式
模型 → 直接加载整个文件 → 上下文爆满模型 → 思考（我需要查记忆）→ 调用 memory_search（外部系统检索）→ 得到线索 → 调用 memory_get（外部系统精准切片）→ 只将提取出的几行（极少 Token）喂给模型生成最终回答

与开场装配的对应关系：

每一轮开场，运行时拼一份提示，其中与「此前发生过什么」有关的部分只有三块：

块内容说明
最近若干轮原文就近的对话保持原话保证代词、追问和刚确认的事项还在
少量长期事实按当前这句话检索，只取回几条相关记录检索不到就这一块为空；用户的全部历史不进入提示
一份较早摘要有字数上限的客观叙述由更早内容压缩而来；保留事实、偏好、约定和未完成事项，去掉寒暄和重复

摘要必须标成背景：放进一个单独的回合，开头写明「这是更早对话的压缩，不是本轮用户原话」，模型才不会把它当成用户刚刚说的话或一条新的系统指令。身份说明仍然是提示开头唯一的系统段——再追加一条系统消息，会和不少接口「系统段只出现在开头」的要求冲突。

一句话总结：不要指望大模型自己“假装”记住了所有东西。通过在 System Prompt 中硬性规定调用 memory_search 和 memory_get，将复杂的内存管理逻辑剥离给外部代码（Python/Node.js 脚本），让大模型只负责“决策需要什么数据”，让外部工具负责“高效过滤和提取数据”。

策略三：工具调用——动态按需加载（Lazy Loading） ​

场景：用户下达“做一支自我介绍的视频”时，Agent 不会盲目执行，而是先去指定目录寻找是否有相关的 SKILL.md 文件。

上下文工程的核心体现（System Prompt 动态组装）：

  • 按需读取（Lazy Loading）：System Prompt 中并没有直接塞入所有技能的具体代码，而是只给了一个目录/清单（列出技能名和路径，并提示“有需要请读取”）。
  • 避免上下文污染：如果一次性把所有 Skill 的详细步骤都塞进 System Prompt，会消耗大量 Token 并可能干扰模型判断。通过“按需读取”，只为当前任务提供最精准的上下文。

工具调用（Tool Use）：

  • 当模型意识到需要“做视频”这个技能时，它会根据 System Prompt 中的路径指引，自主发出 [tool_use] Read(video/SKILL.md) 的指令去读取具体操作指南，随后直接执行该工具。

与技能/资料按需进入的对应关系：

  • 技能的步骤、领域手册都不放进开场提示。
  • 开场只放技能名称和一句话适用时机；模型判定这一轮用得上，再读取那一份说明，读入的是这一份，不是目录里的全部。
  • 领域资料由执行节点按当前问题检索。命中的条目进入该节点的提示，手册的其余部分留在库里。检索为空，节点就在没有资料的情况下回答，或者明确说没有查到，而不是退回去把整本手册装进窗口。

一句话总结：AI Agent 不是一次性接收所有工具说明，而是通过 System Prompt 提供技能索引，让模型在需要时（按需）主动去读取具体的 SKILL.md，这是上下文工程中优化 Token 和提升模型执行准确率的关键技巧。

三、辅助机制 ​

3.1 周期滑动窗口摘要 ​

工作记忆有轮次上限。挤出的一轮不能直接丢掉，否则追问会断；也不能把挤出的原文继续堆在提示里，否则窗口只是换了个地方变长。

  • 设定固定的 token 阈值（如 100k），触发总结最近的对话历史。
  • 将摘要替换掉原始文本。
  • 合并可以攒几轮再做一次，避免每一轮都为了压缩再调用一次模型。
  • 新摘要仍然受同一个字数上限约束，所以提示里的摘要段不会随对话无限变长。

3.2 压缩指南的自动迭代 ​

以“完整上下文成功、压缩上下文失败”的对比轨迹作为反馈：

  • 当完整上下文能做对、压缩之后做错时，把这两次轨迹放在一起；
  • 让 LLM 分析“压缩时漏掉了哪条事实或约定”；
  • 然后改写压缩说明；
  • 说明变好之后，下一次合并沿用新说明。

四、核心原则总结 ​

原则说明
按需供给窗口里只放当前这一步要看的内容
三块记忆最近原文 + 少量检索事实 + 一份受限摘要
摘要滚动挤出轮次压缩合并，受同一字数上限约束；压缩说明可迭代改进
专用节点中间文本在节点内消化，只交回结论，主会话呈锯齿状
并行不转发分支各自看开场状态，结束时汇合结论
执行节点不派生多步由规划阶段串行写明
技能资料按需读开场只放名称和适用时机，用时再读单份

五、收尾：一句话总结 ​

一个核心矛盾：无限的任务复杂度 vs 有限的上下文窗口。

三大解决策略：

  1. 宏观架构：Subagent 与上下文折叠。
  2. 记忆读取：按需检索与精准切片（memory_search + memory_get）。
  3. 工具调用：动态按需加载（Lazy Loading）。

总结成一句话：

高级 AI Agent 的上下文工程，本质上是建立了一套“外部动态供给系统”——让大模型始终只看到与当前决策最相关、最精简的信息，把海量的中间过程和冗余知识留在模型外部（由 Subagent 或外部工具处理），从而用有限的上下文窗口撬动无限复杂的任务。
