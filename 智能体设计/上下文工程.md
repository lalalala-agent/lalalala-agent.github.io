# 上下文工程

任务可以无限长：检索、读资料、看画面、分几步做完。模型一次能看见的上下文是有限的。上下文工程要解决的就是这件事：在有限的窗口里，只放这一次决策真正要用的信息。

窗口被塞满时会出现三件事：

| 问题 | 表现 |
| --- | --- |
| 装不下 | 超过窗口上限，这一轮直接失败，或被迫从中间截断，截掉的可能是目标 |
| 注意力被冲淡 | 无关原文、旧话题、整页网页夹在提示中间，模型丢掉当前要完成的那一句；中段内容尤其容易被忽略 |
| 费用和延迟上升 | 每轮重发一大段历史；定时唤醒如果也带上全部历史，花费会按唤醒次数乘上去 |

对应的原则是按需供给：海量的中间过程留在模型外面，由运行时、专用节点或工具消化，窗口里只留下当前这一步要看的内容。

## 一轮开始时装配什么

每一轮开场，运行时拼一份提示，里面与「此前发生过什么」有关的部分只有三块：

| 块 | 内容 | 说明 |
| --- | --- | --- |
| 最近若干轮原文 | 就近的对话保持原话 | 保证代词、追问和刚确认的事项还在 |
| 少量长期事实 | 按当前这句话检索，只取回几条相关记录 | 检索不到就这一块为空；用户的全部历史不进入提示 |
| 一份较早摘要 | 有字数上限的客观叙述 | 比「最近若干轮」更早的内容压缩而来；保留事实、偏好、约定和未完成事项，去掉寒暄和重复 |

摘要必须标成背景：放进一个单独的回合，开头写明「这是更早对话的压缩，不是本轮用户原话」，模型才不会把它当成用户刚刚说的话或一条新的系统指令。身份说明仍然是提示开头唯一的系统段——再追加一条系统消息，会和不少接口「系统段只出现在开头」的要求冲突。

这三块之外，还有本轮的用户原话、身份说明、允许使用的工具名单。领域资料和技能正文不在开场时装入。

## 摘要怎么滚动

工作记忆有轮次上限。挤出的一轮不能直接丢掉，否则追问会断；也不能把挤出的原文继续堆在提示里，否则窗口只是换了个地方变长。

```mermaid
flowchart LR
    A["已有摘要"] --> C["压缩调用<br/>固定说明：综合要点 · 保留事实/偏好/约定/未完成事项 · 去掉寒暄 · 不编造 · 不超过字数上限"]
    B["新挤出的一轮或几轮"] --> C
    C --> D["新摘要<br/>受同一字数上限约束"]
```

合并可以攒几轮再做一次，避免每一轮都为了压缩再调用一次模型。新摘要仍然受同一个字数上限约束，所以提示里的摘要段不会随对话无限变长。

压缩说明本身也要能改。当完整上下文能做对、压缩之后做错时，把这两次轨迹放在一起，让模型指出压缩时漏掉了哪条事实或约定，然后改写压缩说明。说明变好之后，下一次合并沿用新说明。

## 专用节点把中间文本折掉

复杂的一步往往自己会产生大量文本：搜索结果、网页、多帧画面、资料条目。如果都回到主提示里，窗口会在这一步之后永久变长。做法是把这一步交给专用节点：节点在自己的上下文里阅读和筛选，结束时只交回结论——一句话、一个动作标签、几条命中的资料。节点用过的原文随节点结束丢弃，不追加到主会话。

上下文长度因此呈锯齿：节点执行期间，那一个节点的上下文上升；节点结束、只把结论交回时，主会话的长度下降，空出位置给下一步。

几个节点并行时（例如一边组织要说的话、一边决定动作），它们不互相转发中间文本。每条并行分支只看见开场装入的那份状态，以及自己这一支的材料；分支之间只在结束时把各自的结论汇合，交给通道一起下发。

执行节点不再往下派生新的节点。派生一层，就会再产生一份无人折叠的中间文本，锯齿下降就消失了。需要多步时，由规划阶段一次写明串行顺序，后一步只接收前一步的结论。

## 技能和资料按需进入

技能的步骤、领域手册都不放进开场提示。开场只放技能名称和一句话适用时机；模型判定这一轮用得上，再读取那一份说明，读入的是这一份，不是目录里的全部。

领域资料由执行节点按当前问题检索。命中的条目进入该节点的提示，手册的其余部分留在库里。检索为空，节点就在没有资料的情况下回答，或者明确说没有查到，而不是退回去把整本手册装进窗口。

## 短会话和感知通道

定时任务和心跳各开一轮新的短会话，这份提示里没有日常对话的长历史。唤醒要看的状态写在任务自己的提示里，或者写在一份很短的清单里——把日常长会话附带进去，等于每次唤醒都把几天的闲聊再付一次费用，而且闲聊会盖住这次任务的目标。

感知通道上的原始画面不进入每一轮对话提示。画面留在感知侧，只有「这一步确实要看」的节点取用最近的帧；对话节点看见的是已经抽出的事件（例如有人出现、需要问候），而不是一串图像。
