# vLLM 推理

> vLLM 是跑在显卡上的推理服务：权重负责计算，服务把多路对话收成一批、把算过的键值按块放在显存里，再通过 OpenAI 兼容接口把结果送出去。

## 一轮请求里的两个阶段

一段提示进来后，计算分成两段：

```mermaid
flowchart LR
    P["Prefill<br/>整段提示一次算完，吃满算力"] -->|"每个 token 的键值留在显存"| D["Decode<br/>一次生成一个新 token，更吃显存带宽"]
```

| 阶段 | 做什么 | 瓶颈 |
| --- | --- | --- |
| Prefill | 整段提示一次算完，时间大致随提示长度上升 | 吃算力 |
| Decode | 一次只生成一个新 token，提示本身不用再算；对话逐字出现就是这段 | 吃显存带宽——每一步要把越来越长的键值读出来 |

两段分开调度后，每一路对话不再独占整张卡直到说完。

## 连续批处理

多路请求按「谁先说完谁退出」叠在同一批里：已在 decode 的请求留在批次中，新请求的 prefill 插进批次空隙，某一路生成结束立刻退出，空位交给排队的请求。

服务报出的吞吐，是一小段时间里所有请求合在一起处理的 token 数，和「一路对话独占显卡时每个字有多快」是两个数。引擎约每 10 秒打一行平均值，空闲时间也算在这 10 秒里；读这行时，要把它和单次请求的 prefill、decode 分开。

## 分页注意力

键值如果按「每路请求预留到最大长度」来占显存，短对话会在显卡上留下长空洞，路数一多就装不下。分页注意力把键值切成固定大小的块：请求变长时再领一块，生成结束就把块还回去，长度不同的请求因此可以挤在同一张卡上。

单请求能占多少块，由上下文上限封顶——提示、系统说明和已经生成的 token 都算进这个上限，超过的请求会被拒绝。

## 启动时要定的几件事

这些是服务的开关，换一张卡、换一个模型就重新选，不写进权重里。

| 开关 | 决定什么 |
| --- | --- |
| 显存占用比例 | 启动时向驱动申请显存的比例，用来放权重和键值块。比例高则键值块更多、能同时挂住的上下文更长；比例低则把余量留给同卡其他进程。权重先占掉一份固定大小，剩下的才是块 |
| 上下文上限 | 单请求的硬上限，也是这一路最多能领的块数；系统提示、工具说明、对话历史都算在里面 |
| 专家并行 | 混合专家模型每个 token 只激活一小部分专家，但显卡要装下全部专家权重。专家并行把专家拆到多张卡上；单卡拆开没有通信收益，开关关掉，多卡才用它摊开专家 |
| 只要语言模型 | 多模态权重常带着视觉编码器；文本服务可启动时不加载视觉部分，显存只留给语言模型和键值块 |
| 量化 | 4/8 比特量化压小权重体积，才能和键值块一起放进一张卡。它改变的是权重怎么存，不改变 prefill 和 decode 的调度方式 |
| 解析器 | 推理解析把思考段和正式回答拆开；工具调用解析把工具调用收成结构化请求。解析器要配对模型的输出格式，换模型族就换解析器 |
| 前缀缓存 | 打开后，相同的系统提示和工具说明可在下一次请求里复用已算过的键值块。缩短的是 prefill，decode 仍逐 token 生成 |

采样参数和「是否输出思考」要写成当前版本直接认识的字段。有的版本会整段忽略请求里的 `extra_body`——参数只放在那里，引擎仍按自己的默认值跑。
