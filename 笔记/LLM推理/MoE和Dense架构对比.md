# MoE vs Dense

## 1. 测试背景

本次对比两款 FP8 模型在不同并发下的推理性能：

- **Dense：** Qwen3.8-27B-FP8
- **MoE：** Qwen3.6-35B-A3B-FP8

两者都使用 FP8 权重，但架构不同。Dense 的 FFN 参数每个 token 都会参与计算；MoE 通过专家路由，仅激活部分专家。因此，总参数量不能直接代表每 token 的计算量。

### 测试环境

| 项目 | 配置 |
|---|---|
| CPU | Intel Core i9-14900K |
| 内存 | 64 GB |
| GPU | NVIDIA RTX 4090 |
| 推理框架 | vLLM 0.31.0 |
| Dense 模型 | Qwen3.8-27B-FP8 |
| MoE 模型 | Qwen3.6-35B-A3B-FP8 |
| 推理模式 | Eager，未使用 CUDA Graph |
| API | `/v1/chat/completions` |

Dense 使用 FP8 权重，具体量化执行路径以 vLLM 启动日志为准。若日志显示 Marlin weight-only 路径，应在环境说明中注明。

### 测试方法

| 项目 | 配置 |
|---|---|
| 每个模型请求数 | 128 |
| 并发数 | 1、4、8、16 |
| 每种并发请求数 | 32 |
| 目标输入长度 | 512 tokens |
| 输出长度 | 128 tokens |
| Think 模式 | 开启 |
| 失败请求 | 0 |
| 请求提交 | 全部提交，客户端限制同时在途请求数 |

两款模型均包含视觉编码器，但本次只测试文本输入。

## 2. 模型结构差异

| 项目 | Dense：Qwen3.8-27B-FP8 | MoE：Qwen3.6-35B-A3B-FP8 |
|---|---:|---:|
| 总参数量 | 27B | 约 35B |
| 每 token 激活参数量 | Dense 参数参与计算 | 约 3B |
| Transformer 层数 | 64 | 40 |
| Hidden size | 5120 | 2048 |
| 全注意力层 | 16 | 10 |
| 线性注意力层 | 48 | 30 |
| 全注意力 KV heads | 4 | 2 |
| Attention head dimension | 256 | 256 |
| FFN / Expert 中间维度 | 17408 | 512 |
| 路由专家 | 无 | 256 个，每 token 选 8 个 |
| 共享专家 | 无 | 1 个 |

主要区别在于每 token 的计算路径：

- **Dense：** 每个 token 都经过 Dense FFN，计算量相对稳定。
- **MoE：** 每个 token 只激活部分路由专家，并额外经过共享专家。

MoE 需要存储所有专家权重，但单 token 不需要计算所有专家。因此，总参数量更大的 MoE 仍可能具有更低的单 token 计算量。

## 3. 单请求解码：为什么速度接近？

TPOT（Time Per Output Token）表示生成阶段平均每个输出 token 所需的时间。TPOT 越低，单请求解码速度越快。

### TPOT 实测结果

| 并发数 | Dense TPOT | MoE TPOT | 对比 |
|---:|---:|---:|---|
| 1 | 33.98 ms | 35.02 ms | Dense 快约 3% |
| 4 | 37.19 ms | 36.03 ms | MoE 快约 3% |
| 8 | 40.73 ms | 36.86 ms | MoE 快约 9.5% |
| 16 | 51.88 ms | 41.36 ms | MoE 快约 20.3% |

并发为 1 时，两者 TPOT 仅相差约 1 ms。也就是说，在当前硬件、推理框架和执行配置下，**Dense 与 MoE 的单请求解码速度基本处于同一水平**。

这不代表两者计算量相同，而是说明实际解码速度还受到权重访存、kernel 效率、量化实现和模型结构等因素影响。

### Dense 的权重带宽估算

假设 Dense 实际加载权重约 29.34 GiB，换算为 GB：

```text
29.34 GiB × 1.0737 ≈ 31.5 GB
```

RTX 4090 理论显存带宽约 1008 GB/s。若一次解码迭代需要读取全部权重，则理想带宽下限为：

```text
T_min = 31.5 GB / 1008 GB/s × 1000 ms/s
      ≈ 31.3 ms
```

该估算与 Dense 在并发 1 时实测的 33.98 ms TPOT 接近。但它只是简化估算，不能据此断定 Dense 完全受显存带宽限制。29.34 GiB 应来自实际权重规模，而非单纯按参数量推算；实际读取量还会受缓存、kernel 实现和批处理方式影响。

FP8 可降低权重存储和访存开销，但实际占用还包括量化 scale、未量化参数及其他模型状态，因此不能简单认为所有权重都严格占用每参数 1 byte。

## 4. FFN 理论计算量：MoE 为什么更低？

可用以下简化公式估算 FFN 主要线性投影的 FLOPs：

```text
F_FFN ≈ 2 × 3 × d × f × L
```

其中：

- `d`：隐藏层维度
- `f`：FFN 或专家中间维度
- `L`：层数
- `2`：一次乘加按 2 FLOPs 计
- `3`：SwiGLU 的 gate、up、down 三个线性投影

### Dense

```text
F_Dense ≈ 2 × 3 × 5120 × 17408 × 64
        ≈ 34.2 GFLOPs/token
```

### MoE

MoE 每层每 token 激活 8 个路由专家和 1 个共享专家：

```text
F_MoE ≈ 2 × 3 × 2048 × 512 × 9 × 40
      ≈ 2.26 GFLOPs/token
```

两者近似计算量之比：

```text
R = F_Dense / F_MoE
  = 34.2 / 2.26
  ≈ 15.1
```

按这组假设，Dense 的 FFN 主要线性投影计算量约为 MoE 的 15.1 倍。

### 为什么计算量相差 15.1 倍，速度却没有相差 15.1 倍？

这里的 15.1 倍，**只代表所选 FFN 线性投影的理论 FLOPs 比值，不是完整模型总计算量比值，更不是实测推理速度比值。** 原因如下：

1. **计算量只是推理耗时的一部分。** 完整推理还包括注意力、线性注意力状态更新、归一化、残差、路由、词表输出等，FFN FLOPs 比值不能代表整个模型。
2. **GPU 并非只受计算量限制。** 若某阶段受显存带宽限制，减少 FLOPs 不一定按比例缩短耗时；若受计算吞吐限制，降低计算量可能收益更明显。
3. **FP8 理论计算量不等于实际执行效率。** 两款模型虽都是 FP8，但 kernel、矩阵尺寸、量化 scale 处理和硬件执行路径可能不同。
4. **MoE 还需专家路由与调度。** 专家矩阵较小，未必总能达到 GPU 最高计算效率；不同并发下，专家批处理效率也会变化。
5. **并发会改变计算与访存利用率。** 增加并发可提高批处理效率，但也会增加显存访问、调度和资源竞争。Dense 与 MoE 对并发的响应不同，速度差距会随并发变化。

因此，这个计算仅用于解释：**MoE 结构具有更低的每 token FFN 计算量潜力。** 这种优势能转化成多少实际速度，需以实测 TPOT、吞吐量和延迟为准。

## 5. 并发吞吐量：MoE 优势逐渐扩大

总吞吐量表示单位时间内所有请求生成的输出 token 数。并发增加后，GPU 可在一次迭代中处理更多请求，但不同模型的扩展效率并不相同。

### 总输出吞吐量

| 并发数 | Dense | MoE | MoE / Dense |
|---:|---:|---:|---:|
| 1 | 28.00 tok/s | 27.85 tok/s | 0.99× |
| 4 | 91.56 tok/s | 106.84 tok/s | 1.17× |
| 8 | 156.07 tok/s | 208.31 tok/s | 1.33× |
| 16 | 234.23 tok/s | 360.59 tok/s | 1.54× |

结果显示：

- 并发 1 时，两款模型总吞吐量几乎相同。
- 并发 4 时，MoE 领先约 17%。
- 并发 8 时，领先约 33%。
- 并发 16 时，MoE 达到 360.59 tok/s，约为 Dense 的 **1.54 倍**。

### 线性扩展效率

以并发 1 的吞吐量为基准，定义线性扩展效率：

```text
E_C = T_C / (C × T_1) × 100%
```

其中：

- `T_C`：并发数为 `C` 时的总吞吐量
- `T_1`：并发数为 1 时的总吞吐量
- `C`：并发数

| 并发数 | Dense 扩展效率 | MoE 扩展效率 |
|---:|---:|---:|
| 1 | 100% | 100% |
| 4 | 81.8% | 95.9% |
| 8 | 69.7% | 93.5% |
| 16 | 52.3% | 80.9% |

Dense 的扩展效率随并发上升明显下降；MoE 在并发 16 时仍保持约 80.9%。

这说明在当前配置下，MoE 更能将增加的并发请求转化为额外吞吐量。可能原因包括每 token 激活参数较少、Dense 权重访存压力较大，以及两者在量化 kernel 和批处理调度方面的差异。现有数据能展示这一现象，但不能证明某一因素是唯一原因。

## 6. 延迟表现：吞吐量提升不等于所有延迟都下降

除 TPOT 和吞吐量外，还需关注 TTFT、ITL 和端到端延迟：

- **TTFT：** 从请求开始到收到第一个输出 token 的时间。
- **TPOT：** 生成阶段平均每个输出 token 的时间。
- **ITL：** 相邻输出 token 之间的间隔。
- **E2E：** 请求从开始到生成完成的总耗时。

### 延迟实测结果

| 并发 | 模型 | 平均 TTFT | TTFT 中位数 | TTFT P99 | 平均 TPOT | ITL P99 | 平均 E2E |
|---:|---|---:|---:|---:|---:|---:|---:|
| 1 | Dense | 256 ms | 261 ms | 291 ms | 33.98 ms | 35.4 ms | 4.57 s |
| 1 | MoE | 148 ms | 85 ms | 1473 ms | 35.02 ms | 70.6 ms | 4.60 s |
| 4 | Dense | 869 ms | 885 ms | 965 ms | 37.19 ms | 74 ms | 5.59 s |
| 4 | MoE | 217 ms | 159 ms | 895 ms | 36.03 ms | 72 ms | 4.79 s |
| 8 | Dense | 1.38 s | 1.42 s | 1.86 s | 40.73 ms | 101 ms | 6.55 s |
| 8 | MoE | 232 ms | 217 ms | 569 ms | 36.86 ms | 73 ms | 4.91 s |
| 16 | Dense | 2.12 s | 2.01 s | 3.61 s | 51.88 ms | 660 ms | 8.71 s |
| 16 | MoE | 362 ms | 296 ms | 897 ms | 41.36 ms | 116 ms | 5.61 s |

并发 16 时，Dense 平均 TTFT 达 2.12 秒，MoE 为 362 ms；Dense 平均 E2E 为 8.71 秒，MoE 为 5.61 秒。这与吞吐量结果一致：MoE 在较高并发下整体表现更好。

TPOT 和 ITL 不能混为一谈。TPOT 是生成阶段的平均时间指标，ITL 反映 token 间隔分布。并发调度可能导致个别 token 间隔明显变长，因此不能仅凭平均 TPOT 推断尾部 ITL。

每个并发级别只有 32 个请求，P99 主要用于观察尾延迟现象，不宜直接视为稳定的生产环境尾延迟指标。

## 7. KV Cache：理论开销与运行时容量

两款模型都采用混合注意力结构，包括线性注意力层和全注意力层，因此不能把所有 Transformer 层都视为标准全注意力层来计算 KV Cache。

对于全注意力部分，假设 K/V 元素各占 1 byte，每个 token 的 K/V 存储量可估算为：

```text
M_KV = N_full × N_KVheads × D_head × 2 × B
```

其中：

- `N_full`：全注意力层数
- `N_KVheads`：每层 KV heads 数量
- `D_head`：每个 head 的维度
- `2`：分别存储 Key 和 Value
- `B`：每个元素占用的字节数，此处假设为 1

### Dense

```text
M_KV = 16 × 4 × 256 × 2 × 1
     = 32768 bytes/token
     ≈ 32 KiB/token
```

### MoE

```text
M_KV = 10 × 2 × 256 × 2 × 1
     = 10240 bytes/token
     ≈ 10 KiB/token
```

### vLLM 报告的缓存容量

| 项目 | Dense | MoE |
|---|---:|---:|
| 全注意力层数 | 16 | 10 |
| KV heads | 4 | 2 |
| 全注意力 K/V 理论开销 | 32 KiB/token | 10 KiB/token |
| vLLM 报告缓存容量 | 11.22 GiB | 5.88 GiB |
| vLLM 报告缓存 token 数 | 239,616 | 376,320 |

以上理论值只覆盖全注意力层的 K/V，不包括线性注意力状态缓存。实际运行时容量还会受缓存数据类型、内存对齐、block 分配、模型实现和可用显存影响。

因此，MoE 报告缓存容量虽只有 5.88 GiB，却支持更多缓存 token，并不矛盾。vLLM 报告的是其运行时实现下的缓存容量指标，不能仅凭全注意力 K/V 理论字节数反推完整缓存容量。

## 8. 结论

本次测试表明，FP8 Dense 与 FP8 MoE 的性能差异会随并发水平变化。

1. **单请求解码速度接近。** 并发 1 时，Dense TPOT 为 33.98 ms，MoE 为 35.02 ms，差距很小。
2. **MoE 在高并发下吞吐量更高。** 并发 16 时，MoE 达 360.59 tok/s，约为 Dense 的 1.54 倍。
3. **MoE 扩展效率更好。** 并发 16 时，MoE 线性扩展效率约 80.9%，Dense 为 52.3%。
4. **高并发下延迟差距更明显。** 并发 16 时，MoE 平均 TTFT 和 E2E 都显著低于 Dense。
5. **理论计算量不能直接等同于实际速度。** MoE 每 token 激活参数较少，但最终性能仍取决于 FP8 kernel、权重访存、专家调度和推理框架实现。

总体来看，在当前硬件和 vLLM 配置下，Dense 在低并发时可提供与 MoE 接近的解码速度；并发增加后，MoE 更能维持吞吐量增长，并表现出更低平均延迟。

这些结论适用于本次测试配置，不应直接外推到其他 GPU、量化实现或推理框架。
