# 机器人 Agent 与 Skill 架构设计

## 1. 文档目标

本文定义机器人 Agent 的整体软件架构，说明 Agent 如何理解用户指令、选择 Skill、组织动作任务，并通过 ROS 2 与运动控制系统交互，最终驱动机器人执行动作。

设计目标：

- **统一接口**：不同动作使用一致的请求和结果结构。
- **能力分层**：Agent 负责任务决策，Skill 负责领域能力，控制器负责运动执行。
- **模块解耦**：语言模型、机器人动作逻辑、通信接口和电机驱动相互独立。
- **支持组合**：多个 Skill 可以按顺序或并行组合，完成复杂行为。
- **安全可控**：动作执行具备状态反馈、超时处理、取消机制和安全约束。

## 2. 系统总体架构

```text
用户指令 / 上层应用
        |
        v
+----------------------+
|      Robot Agent     |
| 意图理解、任务规划、调度 |
+----------------------+
        |
        v
+----------------------+
|     Skill Manager    |
| Skill 注册、选择、执行 |
+----------------------+
        |
        v
+----------------------+
|      Skill Layer     |
| 头部控制 / 眼部控制   |
| 表情控制 / 其他能力   |
+----------------------+
        |
        v
+----------------------+
|    ROS 2 Interface   |
| Action / Service /   |
| Topic                |
+----------------------+
        |
        v
+----------------------+
| Motion Controller    |
| 轨迹规划、限幅、插补  |
+----------------------+
        |
        v
+----------------------+
| Hardware Adapter     |
| TCP / CAN / CANopen  |
| CiA 402 等            |
+----------------------+
        |
        v
     电机与执行机构
```

系统分为六个主要层次：

1. **Agent 层**：理解用户意图，将自然语言转换为可执行任务。
2. **Skill Manager 层**：维护 Skill 注册信息，完成能力选择、参数校验和任务调度。
3. **Skill 层**：封装某一类机器人能力，对外提供统一的动作调用方式。
4. **ROS 2 通信层**：负责动作请求、执行状态、结果返回和设备状态发布。
5. **运动控制层**：将动作目标转换为满足运动约束的轨迹和控制指令。
6. **硬件适配层**：将控制指令映射到具体设备通信协议和驱动接口。

Agent 不应直接控制电机寄存器或发送底层总线报文。底层运动约束、设备协议和故障处理应由控制系统负责。

## 3. Agent 与 Skill 的职责

### 3.1 Robot Agent

Robot Agent 是任务级决策和调度模块，主要负责：

- 理解用户自然语言指令。
- 识别任务目标和动作顺序。
- 根据 Skill 能力描述选择合适的 Skill。
- 提取并检查动作参数。
- 处理动作之间的依赖关系。
- 监控执行状态，并根据结果决定继续、重试、取消或报告失败。
- 将执行结果转换为用户可理解的反馈。

Agent 负责决定“做什么”以及“按什么顺序做”，不负责生成每个电机控制周期的底层指令。

### 3.2 Skill

Skill 是面向某一类机器人能力的封装单元。它定义能力范围、可用动作、参数约束和执行方式，并将请求转换为控制系统能够理解的动作目标。

Skill 应按**能力领域**组织，而不是为每个微小动作单独创建一个 Skill。

例如：

| Skill | 负责的能力 | 典型动作 |
|---|---|---|
| `head_control` | 头部运动 | 左右转头、点头、摇头、回到中立位 |
| `eye_control` | 眼部运动 | 视线移动、眨眼、眼球回中 |
| `expression_control` | 表情与动作协调 | 微笑表情、疑问表情、惊讶表情 |
| `body_control` | 躯干或身体运动 | 转身、身体倾斜、姿态调整 |

组合能力可以调用多个底层 Skill。例如，疑问表情可以协调头部轻微倾斜、眼睛注视和表情执行，而不必将每一种组合都拆成独立的底层动作 Skill。

### 3.3 Skill 的标准描述

每个 Skill 应提供机器可读的能力描述，至少包括：

- `skill`：唯一的能力名称。
- `description`：能力说明。
- `actions`：支持的动作列表。
- `parameters`：各动作的参数定义、类型、单位和范围。
- `constraints`：执行限制及前置条件。
- `execution_type`：动作是否需要持续执行和状态反馈。

示例：

```json
{
  "skill": "head_control",
  "description": "控制机器人头部姿态",
  "actions": [
    "look_at",
    "nod",
    "shake_head",
    "neutral"
  ],
  "parameter_units": {
    "yaw": "degree",
    "pitch": "degree",
    "roll": "degree"
  }
}
```

该描述用于能力发现和参数校验。实际可用动作、角度范围及单位约定应由机器人配置和对应控制器确定。

## 4. 统一动作接口

### 4.1 设计原则

所有 Skill 使用统一的请求外层结构，但不同动作可以具有不同的业务参数。

统一接口用于规范请求标识、动作名称、参数容器和执行时长，不意味着所有动作必须使用完全相同的参数。

### 4.2 请求结构

```json
{
  "request_id": "req_001",
  "skill": "head_control",
  "action": "look_at",
  "parameters": {
    "yaw": -30.0,
    "pitch": 5.0,
    "roll": 0.0
  },
  "duration": 1.0
}
```

字段定义：

| 字段 | 类型 | 说明 |
|---|---|---|
| `request_id` | string | 请求唯一标识，用于关联执行状态和结果 |
| `skill` | string | 目标能力模块 |
| `action` | string | 该 Skill 支持的具体动作 |
| `parameters` | object | 与动作对应的参数集合 |
| `duration` | number | 期望动作时长，单位为秒 |

参数说明：

- `yaw`：偏航角，表示头部左右旋转。
- `pitch`：俯仰角，表示低头或抬头。
- `roll`：横滚角，表示头部向肩部方向倾斜。

角度单位统一使用度（degree）。正负方向应在机器人坐标系配置中明确规定，不能假定所有设备的方向约定相同。

`duration` 表示期望执行时长，不保证设备一定能在该时长内完成动作。控制器必须结合速度、加速度、限位和安全约束决定实际轨迹。

### 4.3 动作参数示例

**转头：**

```json
{
  "request_id": "req_002",
  "skill": "head_control",
  "action": "look_at",
  "parameters": {
    "yaw": -30.0,
    "pitch": 0.0,
    "roll": 0.0
  },
  "duration": 1.0
}
```

**点头两次：**

```json
{
  "request_id": "req_003",
  "skill": "head_control",
  "action": "nod",
  "parameters": {
    "count": 2,
    "yaw": 0.0,
    "pitch": 15.0,
    "roll": 0.0
  },
  "duration": 1.2
}
```

在该示例约定下，正 `pitch` 表示低头。`count` 表示重复次数，`pitch` 表示点头幅度。

角度参数描述目标姿态或动作幅度，不代表完整运动轨迹。控制器仍需生成低头和回正等运动阶段，并确保轨迹满足设备约束。

**眨眼两次：**

```json
{
  "request_id": "req_004",
  "skill": "eye_control",
  "action": "blink",
  "parameters": {
    "count": 2
  },
  "duration": 0.8
}
```

动作参数应由对应 Skill 的参数定义约束。对于不支持的动作或缺失的必要参数，系统应返回明确的校验错误，而不是自行猜测执行方式。

## 5. 动作结果与状态反馈

动作请求被接受不代表动作已经完成。系统需要区分请求处理状态与实际执行状态。

建议使用以下状态：

| 状态 | 含义 |
|---|---|
| `accepted` | 请求已接收并通过初步校验 |
| `running` | 动作正在执行 |
| `succeeded` | 动作已完成 |
| `failed` | 动作执行失败 |
| `cancelled` | 动作已取消 |
| `timeout` | 动作超过允许的等待或执行时间 |

结果示例：

```json
{
  "request_id": "req_003",
  "status": "running",
  "progress": 0.5,
  "message": "正在执行第二次点头"
}
```

执行完成后：

```json
{
  "request_id": "req_003",
  "status": "succeeded",
  "message": "点头动作完成"
}
```

`progress` 为可选字段。只有在执行系统能够提供可信进度时才应返回；不能简单地将经过时间比例当作实际动作完成度。

当动作失败时，结果应尽可能包含错误类别和可诊断信息，例如参数超限、设备未就绪、通信中断或执行超时。

## 6. ROS 2 通信设计

ROS 2 是 Agent、Skill、运动控制器和设备驱动之间的通信基础。应根据数据语义选择不同的通信机制。

### 6.1 Action：执行持续时间较长的动作

适合转头、点头、眨眼序列以及需要监控完成状态的动作。

Action 可提供：

- 目标请求。
- 执行反馈。
- 最终结果。
- 取消请求。

典型流程：

```text
Agent
  |
  | 发送 Action Goal
  v
Skill / Action Server
  |
  | 返回执行反馈
  v
Agent
  |
  | 接收最终结果
  v
任务调度器
```

需要注意，取消请求不等于动作立即停止。执行端必须定义取消处理流程，并在允许的情况下让设备安全减速或进入安全状态。

### 6.2 Service：短时请求和配置操作

适合查询能力、读取配置、设置参数或触发短时操作。

例如：

- 查询头部允许的角度范围。
- 查询当前设备状态。
- 更新动作配置。
- 检查 Skill 是否可用。

对于执行时间不确定、需要持续反馈或支持取消的动作，优先使用 Action，而不是长时间阻塞的 Service。

### 6.3 Topic：状态与遥测数据

适合持续发布：

- 当前关节位置。
- 电机速度和状态。
- 设备健康信息。
- 故障状态。
- 控制器运行状态。

Topic 用于异步状态分发，不应单独承担需要明确确认和最终结果的动作执行请求。

### 6.4 通信机制对照

| 机制 | 主要用途 | 是否适合持续反馈 |
|---|---|---|
| Action | 长时间运行的动作任务 | 是 |
| Service | 短时请求与配置操作 | 通常否 |
| Topic | 状态、遥测与事件广播 | 是，但没有内建的任务完成语义 |

具体 ROS 2 接口名称、消息类型和 QoS 配置应在工程实现阶段统一定义。

## 7. Agent 任务分解与组合执行

用户通常描述的是一个复合任务，而不是一个单独的电机动作。

例如，用户说：

> 向左看，点两次头，然后眨两次眼。

Agent 可将其转换为以下任务序列：

```text
用户指令
   |
   v
意图解析
   |
   v
任务规划
   |
   +--> head_control.look_at
   |
   +--> head_control.nod(count=2)
   |
   +--> eye_control.blink(count=2)
   |
   v
收集执行结果
   |
   v
返回任务总结
```

默认按顺序执行，以保证动作语义清晰：

1. 头部转向左侧。
2. 确认转头动作完成。
3. 执行两次点头。
4. 确认点头动作完成。
5. 执行两次眨眼。
6. 汇总各动作的最终结果。

若动作之间没有依赖关系，且硬件支持并行执行，也可以由 Agent 规划并发任务。但并发执行必须考虑共享关节、设备资源冲突、动作同步和安全约束，不能仅因为多个 Skill 不同就默认可以并行。

如果某个动作失败，Agent 应依据任务策略决定停止后续动作、执行安全恢复或继续执行无依赖的动作，并在最终结果中明确报告失败情况。

## 8. 从 Agent 到电机的完整执行链路

完整执行链路如下：

1. **指令理解**：Agent 识别用户希望机器人完成的动作。
2. **任务规划**：将复合指令拆解为一个或多个 Skill 调用。
3. **参数校验**：检查动作名称、参数类型、角度范围和时长。
4. **动作提交**：通过 ROS 2 Action 或其他约定接口发送目标。
5. **运动规划**：运动控制器根据当前状态、目标姿态和运动限制生成轨迹。
6. **协议转换**：硬件适配层将控制目标转换为设备支持的通信协议和指令格式。
7. **设备执行**：驱动器控制电机完成运动。
8. **状态反馈**：控制器获取实际位置、运行状态和故障信息。
9. **完成判定**：根据设备反馈和动作完成条件判断成功、失败或超时。
10. **结果返回**：Agent 汇总各动作的最终状态并向用户报告。

系统应区分以下三个事件：

- 请求已接收。
- 设备已开始执行。
- 动作已实际完成。

只有满足定义好的完成条件后，才能将动作标记为 `succeeded`。不能仅凭消息发送成功就认定机器人动作完成。

## 9. 安全与异常处理

所有动作请求都必须经过控制系统的安全检查。至少应考虑：

- 参数范围、关节限位和速度、加速度限制。
- 设备是否已初始化并处于允许运行状态。
- 动作执行期间是否发生通信中断。
- 动作是否超过最大执行时间。
- 是否收到取消或急停请求。
- 多个动作是否争用同一执行机构。
- 故障发生后设备应停止、减速还是进入其他安全状态。

安全检查应在 Skill 层和运动控制层按职责分担。不能只依赖 Agent 或语言模型保证动作安全。急停和驱动器保护等关键机制应由独立、可靠的控制路径实现。

## 10. 与底层运动控制的边界

本文定义的是任务和能力层接口，不规定具体的电机控制算法或总线报文。

以下内容属于底层运动控制文档：

- 目标姿态与实际关节位置的转换。
- 点头、转头等动作的轨迹生成与插补。
- 控制周期、速度和加速度约束。
- TCP 通信报文设计。
- CAN、CANopen、CiA 402 与 CSP。
- CANable 的连接和配置。
- 编码器计数与机械角度转换。
- 驱动器状态监控、故障处理和安全停止。

通过明确分层，Agent 与 Skill 可以保持相对稳定，而运动控制算法和硬件适配层能够根据不同机器人平台独立演进。
